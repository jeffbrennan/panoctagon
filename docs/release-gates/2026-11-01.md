# Svelte release-gate work — November 1, 2026

**Status: not ready for a production traffic switch.** This is a local rehearsal
and evidence for review, not a production sign-off. The remaining decisions and
checks are listed below. No deployment or production data mutation was performed.

## Environment and method

- Apple M1 Pro, 32 GB RAM, macOS/Darwin 27, Node 26.13.0, Python 3.12.10,
  DuckDB 1.1.0, headless Playwright Chromium. Dash ran with two Gunicorn workers;
  Svelte used its production build and one local Uvicorn worker. These are local
  process measurements, not container or production-network budgets.
- Baseline: archived commit `74c0bb5be479ff31aaf61b0b7b091c2b43ebc351`.
  Svelte includes the same-day ordering fix in `c3ee1c6`. Both read separate
  filesystem copies of the same local data: 2,637 fighters, 8,512 completed
  fights, last event download 2026-02-08, and an empty upcoming calendar. The
  390×844 phone case is emulation, not a physical phone. Rendered pages were
  inspected at 1440×900 and 390×844; these do not replace owner sign-off.
- A second, disposable copy received a synthetic future event involving two
  existing fighters, with no odds and one missing image. Separate synthetic
  completed fights exercised partial and entirely missing statistics. No fixture
  was written into the working database. Browser scenarios and metrics depend on
  this particular local dataset and will differ on newer data.

The following differences were found by comparing the visible views and source.
These are **recommended decisions**, not product-owner approval:

- **Keep before cutover:** Dash fight history has native per-column sorting and
  filtering. Svelte's history is chronological and lacks those controls. Decide
  whether to restore them or explicitly accept this loss.
- **Change:** Dash displays favorite/underdog labels on the career plot; Svelte
  supplies odds in the fight history and point tooltip instead. Accept the
  reduced chart clutter only after reviewing discoverability and keyboard access.
- **Change:** Dash's network uses directed win arrows, node opposition-strength
  colors, and a detailed year-by-year hover. Svelte uses undirected matchup
  links, fight-count sizing, a selected-fighter opponent table and profile links.
  The direction and hover detail are not direct visual equivalents; review the
  loss of at-a-glance direction and strength before accepting the replacement.
- **Change:** Dash's roster advantage legend can display multiple series; Svelte
  chooses one metric at a time. Dash's striking scatter includes quadrant labels;
  Svelte omits those labels and adds a searchable/sortable fighter table. Review
  whether single-metric comparison and the revised chart explanation are enough.

## Performance

Raw samples are in [the accompanying directory](2026-11-01/). For the browser
measurements, each sample created a fresh browser context against already-running
servers, opened empty Upcoming, then navigated to the first fighter chart and the
middleweight roster chart. Times end when the named content or first canvas/Plotly
plot is visible; bytes sum response-body transfer sizes through that point.
There were 20 samples per app and no JavaScript errors in these samples. The
browser contexts are cold, while the server and operating-system file caches are
warm. A separate single first-browser sample after restarting both processes is
shown below; one sample is not a cold-latency distribution.

| Browser metric | Dash warm p50 / p95 | Svelte warm p50 / p95 | First browser after restart: Dash / Svelte |
| --- | ---: | ---: | ---: |
| Empty Upcoming visible | 1,186 / 1,212 ms | 62 / 65 ms | 1,233 / 220 ms |
| First fighter chart after click | 74 / 87 ms | 401 / 406 ms | 53 / 405 ms |
| First roster chart after click | 103 / 131 ms | 334 / 368 ms | 121 / 275 ms |
| Total transferred through roster, median | 8,275,694 bytes | 327,329 bytes | 8,259,307 / 327,314 bytes |

These transition timings are **not a like-for-like fighter computation**: Dash
preloads data and charts before switching tabs and chooses a random initial
fighter; Svelte loads Max Holloway and its chart family on demand. The total
from navigation to the first fighter chart is about 1,259 ms for Dash versus
463 ms for Svelte at the medians, but a user already on Upcoming sees the
slower Svelte transition. Both first-chart and roster transitions exceed the
plan's 20% investigation threshold. A trace found the Svelte fighter profile
request completed at about 102 ms and its chart modules by 150 ms, with the
first canvas at 283 ms; roster data arrived around 60 ms and its chart modules
by 92 ms, with canvas at 372 ms. The measurement includes Playwright's scroll
and visibility checks. This supports a loading/rendering tradeoff, not a proven
single bottleneck; profile on representative target devices before accepting it
or making an optimization.

For Svelte, 20 first-request samples each were collected from fresh server
processes, with the operating-system file cache left warm. The browser was not
involved. Warm HTTP samples use 20 requests against an already-running server;
its two-minute analytics cache was enabled, including any first-request miss or bucket rollover. See the raw files for every sample.
The cold and warm request results below are not comparable to the browser
transition measurements.

| Request | Fresh-process p50 / p95 | Warm p50 / p95 | Uncompressed response bytes |
| --- | ---: | ---: | ---: |
| Empty Upcoming | 173.64 / 181.77 ms | 18.16 / 18.90 ms | 2 |
| Middleweight roster | 264.26 / 275.46 ms | 2.01 / 31.51 ms | 53,109 |
| Heavyweight network, 1997–2026 | 171.52 / 177.98 ms | 3.16 / 3.80 ms | about 132,521 |

The separate Dash all-years network function and JSON serialization took a
median 908 ms, p95 918 ms over 20 calls after its data was loaded. Its output was
about 479,562 bytes. Svelte's endpoint includes HTTP and uses a different graph
implementation and cache, so those two numbers are directional evidence only,
not a controlled head-to-head request comparison.

Twenty Svelte navigation cycles across Fighter, Network, Roster and Upcoming
produced no JavaScript errors or HTTP failures. Canvas count grew from three to
five as lazy charts entered view, then stayed at five. The cycle durations were
bimodal: roughly 231–250 ms for early revisits and roughly 881–884 ms later.
An additional trace found no repeat API requests and attributed the increase to
time in the browser interactions/visibility waits, not repeated data fetches;
it did not isolate the rendering or scrolling cause. Investigate this repeatable
variation before claiming the performance gate passed. Set latency and resource
budgets from measurements on the deployment machine and representative current
data; these laptop numbers are not deployment budgets.

## Local routing and rollback rehearsal

A disposable Traefik v3.6 container used a file-provider reproduction of the
legacy host router, higher-priority `/api` strip-prefix router, and `/dagster`
path router. Its backends were the isolated local Dash, API and Svelte processes
and a stub that echoes the Dagster request path. The test switched legacy →
Svelte → legacy and checked HTML, `/api/health`, `/api/metadata`, rejection of
`/api/api/health`, and unchanged `/dagster/server_info`. All returned expected
results. A second test pointed the Svelte process at two immutable copied-data
snapshots and atomically selected revision A → B → A through the proxy. Metadata
changed from 2,637 to 2,638 fighters and back without restarting the reader.
Raw results are recorded alongside the measurements.

The image built locally from `c3ee1c6` had image ID
`sha256:0df4e4e6c3d2fe390f1a9085d1c2fa3df95d90eb2a7e49e4b2296010c4aa76cf`.
With read-only mounts for the copied snapshots and headshots, it passed readiness,
metadata, a synthetic populated card, fighter chart, Network and Roster on a
390×844 Chromium viewport. Its runtime contained the frontend build and had no
`node` or `npm` executable. This is a local image ID, not a pushed release digest.

This does **not** test production TLS, the Docker-label provider, the actual
Dagster service, real image digests, ingestion pause/drain, or the deployed
proxy/network. The prior isolated subprocess test covers snapshot reads while a
separate process writes to the working copy, but a failed full Dagster refresh
and a real scheduled publication cycle remain to be exercised. Existing
zero-upcoming blocking behavior also needs an operational decision. Rehearse
and record the actual rollback sequence in staging, including pausing and
draining ingestion before restoring old readers of the working database.

## Reproduction and remaining gate

The scripts in [scripts/release-gates](../../scripts/release-gates/) reproduce
the sampling and local proxy checks with the ports and copied dataset described
above. They deliberately target `.scratch/release-gates` and must not be pointed
at the active working database. `browser-benchmark.cjs` expects the data's empty
Upcoming, Max Holloway and the 171-fighter middleweight roster; it is a baseline
harness rather than a general-purpose benchmark. `cold-api-benchmark.py` starts
20 short-lived local readers on port 18758. `api-benchmark.py`,
`dash-network-benchmark.py`, and `repeated-navigation.cjs` collect the other
samples. The proxy configuration and script reproduce the local routing model;
they require the isolated servers and echo stub, and do not connect to the
production Traefik network.

Before cutover: obtain parity decisions, perform physical-device and assistive
technology checks, investigate the measured transition/revisit regression,
repeat the performance measurements and set budgets on representative deployment
hardware/data, inventory external API consumers, bootstrap a validated snapshot,
and complete the real proxy, ingestion/failure, and rollback rehearsal described
in the [cutover runbook](../svelte-cutover-runbook.md).
